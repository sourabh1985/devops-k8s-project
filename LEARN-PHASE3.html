2. What is GitOps? ArgoCD — Before vs After

🔑 GitOps in one sentence
Git is the single source of truth. The cluster must always match what's in git. Any difference (drift) is detected and corrected automatically.
❌ Phase 2 — NOT GitOps
  • GitHub Actions SSHs into EC2
  • Runs kubectl apply manually
  • If someone runs kubectl delete pod — it's gone from cluster but NOT from git
  • Cluster state diverges silently from git over time
  • ArgoCD installed, zero config, zero usage
✅ Phase 3 — True GitOps
  • ArgoCD watches this repo every 3 minutes
  • Detects any diff between git and cluster
  • Auto-corrects drift (selfHeal for dev)
  • Manual kubectl changes get reverted
  • ArgoCD Application CRDs = contracts between git and cluster

How ArgoCD Application CRD works

An Application is an ArgoCD resource that says: "Watch this git repo path, deploy it to this namespace."

source.repoURL github.com/sourabh1985/devops-k8s-project Which repo to watch
source.path k8s/dev k8s/prod Which folder in repo to deploy

syncPolicy.automated ✅ Yes (auto-sync) ❌ No (manual) Auto-deploy on git push?

4. Sync Policies — Auto (dev) vs Manual (prod)

Featuredev (app-dev.yaml)prod (app-prod.yaml)
Sync trigger Automatic — ArgoCD polls git every 3 min Manual — click Sync in ArgoCD UI or run CLI
prune ✅ Enabled — deleted files → deleted k8s resources ❌ Disabled — safer for prod
selfHeal ✅ Enabled — reverts manual kubectl changes ❌ Disabled — allows hotfixes if needed
Use case Fast dev iteration, no approval needed Production safety gate, human reviews before promoting
Trigger prod deploy — argocd app sync app-prod or ArgoCD UI → Sync
⚠️ Why manual for prod?
Imagine pushing a bug fix commit that accidentally breaks a config. In dev it auto-deploys — you catch the error fast. In prod, the manual gate gives you a window to review the ArgoCD diff before it goes live. You can see exactly what will change before clicking Sync.

selfHeal explained — what happens when you run kubectl manually

# You run this manually on the cluster (maybe to test something):
kubectl scale deployment service1 --replicas=5 -n dev

# Without selfHeal: cluster now has 5 replicas, git says 1 → they diverge
# With selfHeal (dev): ArgoCD detects drift within 3 minutes → scales back to 1

# This forces all changes to go through git — no "secret" manual changes

5. Canary Deployment — service1 (Order Service)

🐦 What is Canary deployment?
Named after "canary in a coal mine". You send a small % of real traffic to the new version first. If nothing blows up, you gradually increase. If errors spike, you abort with zero downtime.

Phase 2 vs Phase 3 — service1 deployment comparison

❌ Phase 2 — Rolling Update
  • Kubernetes replaces pods one by one
  • During rollout: ~50% old pods, ~50% new pods
  • No control — can't pause at 20%
  • If new version is bad: you only notice after all pods are replaced
  • Rollback = kubectl rollout undo (affects all traffic)
✅ Phase 3 — Canary via Argo Rollouts
  • Controlled traffic split in defined steps
  • Pause windows to observe metrics between steps
  • Abort at any step = instant rollback to 0% new version
  • Old pods stay running during entire ramp-up
  • Uses kind: Rollout instead of kind: Deployment

Canary traffic flow — step by step

StepTraffic to new versionTraffic to old versionDurationAction
Start0%100%—New image pushed, Rollout begins
Step 120%80%1 minute pauseObserve errors, latency
Step 250%50%1 minute pauseObserve, compare both versions
Step 3100%0%—Full rollout complete, old pods removed
Abort (any step)0%100%Instantkubectl argo rollouts abort service1 -n prod

Key YAML difference — Deployment vs Rollout

# Phase 2 — standard Deployment (no traffic control)
apiVersion: apps/v1
kind: Deployment
spec:
  strategy:
    type: RollingUpdate    # Kubernetes default — no pause, no % control

# ─────────────────────────────────────────────────────────────

# Phase 3 — Argo Rollouts Canary (full traffic control)
apiVersion: argoproj.io/v1alpha1
kind: Rollout               # ← different kind
spec:
  strategy:
    canary:
      steps:
        - setWeight: 20     # send 20% traffic to new pods
        - pause: {duration: 1m}   # stop here, wait, observe
        - setWeight: 50     # send 50% traffic to new pods
        - pause: {duration: 1m}   # stop here, wait, observe
        - setWeight: 100    # full rollout

6. Blue-Green Deployment — service2 (User Service)

🔵🟢 What is Blue-Green deployment?
You run two full copies of the app simultaneously — Blue (current live) and Green (new version). All live traffic goes to Blue. You test Green in isolation. When ready, flip the switch — 100% of traffic moves to Green instantly. Blue stays warm for 60 seconds (instant rollback).

Canary vs Blue-Green — when to use which

AspectCanary (service1)Blue-Green (service2)
Traffic shift Gradual (20% → 50% → 100%) Instant (0% → 100% in one switch)
Real user exposure Small % of real users hit new version during ramp No real users on new version until promoted
Resource cost Low — same pods, traffic weights shift Higher — 2× pods running during deployment window
Rollback speed Fast — abort shifts traffic back Instant — switch active service back to Blue
Test before go-live Can't test in isolation (% goes to real users) ✅ Yes — test Green via preview service before promoting
Best for High-traffic services, gradual validation Services needing pre-production QA before full switch

Blue-Green flow — step by step

New image pushed to Docker Hub
↓ ArgoCD detects change in prod
Argo Rollouts spins up GREEN pods (full 3 replicas)
BLUE pods still running — live traffic unaffected
↓ Green is ready
service2-preview → GREEN pods
Test new version: curl http://<master>:30080/api/service2-preview
↓ Tests pass → promote
kubectl argo rollouts promote service2 -n prod
service2-active switches → GREEN pods
BLUE pods enter 60s cool-down
↓ 60 seconds later
BLUE pods scaled down ✅
GREEN is now the new BLUE (stable)

Two services for service2 — why?

Service namePoints toRoleIngress routes to it?
service2-active Blue (stable) pods Live traffic — users hit this ✅ Yes — /api/service2 → service2-active
service2-preview Green (new) pods Testing only — QA before promotion ❌ No — accessed directly for testing 
# Phase 3 — Blue-Green Rollout manifest snippet
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    blueGreen:
      activeService: service2-active    # live traffic (Blue)
      previewService: service2-preview  # new version (Green)
      autoPromotionEnabled: false       # ← require manual promotion in prod
      scaleDownDelaySeconds: 60         # keep Blue warm for 60s after switch

JobPhase 2Phase 3Change
Job 1 Build & Push Docker images Build & Push Docker images SAME

💡 Key difference in Job 2
Phase 2 Job 2 did everything in one go: install tools AND deploy manifests.
Phase 3 separates concerns: Job 2 = infrastructure bootstrap (idempotent), Job 3 = register GitOps contracts, then ArgoCD takes over from there. After the first run, Jobs 2 and 3 complete in seconds (all "already installed, skipping").
