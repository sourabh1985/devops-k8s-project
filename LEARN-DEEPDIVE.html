Without ==3.0.3, pip might install Flask 4.x tomorrow and break your app silently. Pinning guarantees identical behaviour on every build — local, CI, and production.

3. Dockerfile — Packaging the App into an Image

backend/service1/Dockerfile
Instructions to build a self-contained Docker image with Python + Flask + app code
Dockerfile
1FROM python:3.9-slimStart from an official Python 3.9 image (Debian slim = minimal OS, ~130MB). This already has Python installed. No need to install Python on the VM.
2WORKDIR /appSet the working directory inside the container to /app. All following commands run from here. Creates /app if it doesn't exist.
3COPY requirements.txt .Copy requirements.txt from your machine into /app/ inside the image. Done BEFORE copying app code — Docker caches this layer. If requirements don't change, pip install is skipped on rebuild (faster builds).
4RUN pip install --no-cache-dir -r requirements.txtInstall Flask (from requirements.txt) into the image. --no-cache-dir = don't store pip's download cache in the image (keeps image smaller). This layer is cached — only re-runs if requirements.txt changes.
5COPY . .Copy everything else (app.py, etc.) from current folder into /app/ in the image. Done AFTER pip install so code changes don't invalidate the pip cache layer.
6EXPOSE 5000Documentation hint — tells Docker/K8s that this container listens on port 5000. Does NOT actually open the port (that's done by containerPort in backend.yaml). It's metadata only.
7CMD ["python", "app.py"]The command that runs when a container starts from this image. Executes "python app.py" which starts Flask on 0.0.0.0:5000. This is what K8s runs inside every pod.

Why copy requirements.txt separately (line 3) before COPY . . (line 5)?

🐳 Docker layer caching explained
Each line in a Dockerfile creates a cached layer. When you rebuild:
  • If requirements.txt didn't change → layers 3+4 (pip install) are reused from cache — instant
  • If only app.py changed → only layer 5 (COPY . .) rebuilds — fast
  • If you did COPY . . first → every code change would re-run pip install — slow
🔗 Connection: Dockerfile → backend.yaml → Docker Hub
  1. GitHub Actions runs: docker build -t sourabhjha108/service1:latest ./backend/service1
  2. Docker reads this Dockerfile, builds the image
  3. GitHub Actions pushes image to Docker Hub as sourabhjha108/service1:latest
  4. backend.yaml line 27 references: image: sourabhjha108/service1:latest
  5. K8s pulls that image from Docker Hub when starting each pod

k8s/backend.yaml
Kubernetes Deployment — tells K8s to run 3 pods for each backend service, what image to use, and how to check health
backend.yaml — service1 section (service2 and service3 follow the same pattern)
1apiVersion: apps/v1Which Kubernetes API group handles this resource. "apps/v1" is the stable API for Deployments, ReplicaSets, StatefulSets.
2kind: DeploymentResource type. A Deployment manages a group of identical pods (a ReplicaSet) and handles rolling updates.
3metadata:Identity information for this Deployment object in K8s
4 name: service1Deployment name. Used in: kubectl get deployment service1. Also used by rollout restart and by ArgoCD to track the resource.
5 namespace: defaultWhich namespace this Deployment lives in. "default" = the built-in namespace. In Phase 3, this becomes "dev" or "prod" in the environment-specific files.
6 labels:Labels on the Deployment OBJECT itself (not the pods). Used for organizing/querying deployments.
7 app: service1Label on the Deployment. Lets you do: kubectl get deployment -l app=service1
8spec:The desired state specification — everything below here is "what I want K8s to do"
9 replicas: 3Run exactly 3 pods at all times. K8s will create new pods if any die. Change this to scale up/down.
10 selector:How this Deployment finds "its" pods. Must match the labels in template.metadata.labels below.
11 matchLabels:The Deployment "owns" any pod that has ALL these labels
12 app: service1⚠ CRITICAL LINK: must match template.metadata.labels.app below AND Service selector.app. This is how all three connect.
13 template:The pod template — every pod created by this Deployment looks exactly like this
14 metadata:Metadata for each pod created
15 labels:Labels stamped on every pod. The Service uses these to find pods to send traffic to.
16 app: service1⚠ CRITICAL: must match selector.matchLabels AND Service.spec.selector. The label that chains Deployment → Pod → Service together.
17 spec:Pod specification — what's inside each pod
18 topologySpreadConstraints:Rules for spreading pods across nodes. Prevents all 3 pods landing on one node (single point of failure).
19 - maxSkew: 1Max difference in pod count between any two nodes. If node1 has 2 pods, node2 can have at most 3 (diff=1). Keeps distribution even.
20 topologyKey: kubernetes.io/hostnameSpread based on hostname (= each EC2 node). Could also use zone for AZ spread.
21 whenUnsatisfiable: ScheduleAnywayIf perfect spread is impossible (e.g., a node is full), still schedule the pod. "DoNotSchedule" would block the pod instead — too strict for 3-node cluster.
22 labelSelector:Which pods to count when calculating spread (only count OUR pods, not others)
23 matchLabels:
24 app: service1Only count pods with app=service1 when checking spread — ignore pods from other services
25 containers:List of containers in this pod. Usually just one. Each pod = one running app instance.
26 - name: service1Container name within the pod. Used in: kubectl logs -c service1. Mainly for identification.
27 image: sourabhjha108/service1:latestDocker image to run. Format: dockerhub-username/repo:tag. K8s pulls this from Docker Hub. "latest" = most recently pushed image.
28 imagePullPolicy: AlwaysAlways pull the image from Docker Hub when pod starts — even if it's already cached on the node. Required for :latest tags so new pushes are always picked up.
29 ports:Container ports to expose (documentation + networking)
30 - containerPort: 5000Flask listens on 5000 (app.py line 24). Must match. This does NOT open a firewall — it's metadata that helps K8s and tools understand port layout.
31 env:Environment variables injected into the container at runtime
32 - name: APP_VERSIONVariable name. Read in app.py line 8 as: os.environ.get("APP_VERSION")
33 value: "v1"Value injected. Shows up in API response. Change to "v2" in a new deploy to distinguish versions during Canary rollout.
34 resources:CPU and memory budgets. Critical for K8s scheduler to place pods correctly and prevent noisy-neighbour issues.
35 requests:MINIMUM guaranteed resources. K8s scheduler only places pod on a node that has at least this much free.
36 cpu: "100m"100 millicores = 0.1 CPU core. Guaranteed minimum. The "m" = milli (1000m = 1 full core).
37 memory: "128Mi"128 Mebibytes RAM guaranteed. Mi = mebibytes (1Mi = 1.048 MB). Pod won't start if node doesn't have 128Mi free.
38 limits:MAXIMUM allowed. If exceeded: CPU is throttled (not killed). Memory: pod is OOMKilled and restarted.
39 cpu: "250m"Max 0.25 CPU cores. If pod tries to use more, CPU is throttled but pod keeps running.
40 memory: "256Mi"Max 256Mi RAM. If pod exceeds this, K8s kills it (OOMKilled) and restarts it. Prevents one pod from crashing the whole node.
41 livenessProbe:LIVENESS = "Is this pod still alive?" Fail = K8s restarts the container. Used to recover from deadlocks/hangs.
42 httpGet:K8s sends an HTTP GET request to check health. Returns 2xx = healthy. Anything else = fail.
43 path: /healthURL path to call. Must match @app.route('/health') in app.py line 19.
44 port: 5000Port to call health check on. Must match Flask's port (app.py line 24).
45 initialDelaySeconds: 15Wait 15 seconds before first check. Gives Flask time to start up. Without this, K8s might check before Flask is ready and restart it in a loop.
46 periodSeconds: 20Check every 20 seconds. If 3 consecutive checks fail (default failureThreshold=3) → container restarted.
47 readinessProbe:READINESS = "Is this pod ready to receive traffic?" Fail = remove from Service's load balancer (but don't restart). Used during startup and rolling updates.
48 httpGet:Same mechanism as liveness — HTTP GET to /health
49 path: /healthSame /health endpoint — if it returns 200, pod is ready. If not, traffic is redirected to other healthy pods.
50 port: 5000Same port as Flask. K8s checks this before allowing ingress/service to route traffic here.
51 initialDelaySeconds: 10Shorter delay (10s) than liveness (15s). Readiness check starts earlier — pod won't receive traffic until /health returns 200.
52 periodSeconds: 10Check readiness every 10s. More frequent than liveness — traffic decisions need to be faster.
🔑 Liveness vs Readiness — the key difference
ProbeOn FailUse case
livenessProbeContainer RESTARTEDApp is deadlocked or crashed — needs a restart to recover
readinessProbePod REMOVED from load balancer (not restarted)App is starting up, or temporarily overloaded — stop sending traffic but don't kill it

5. backend-service.yaml — ClusterIP Service (every line)

k8s/backend-service.yaml
Creates a stable virtual IP for each backend service — pods change, the service address stays constant
backend-service.yaml — service1 section (service2 and service3 follow the same pattern)
1apiVersion: v1Core Kubernetes API (v1) handles Services, Pods, ConfigMaps, Namespaces. No "apps/" prefix — these are fundamental resources.
2kind: ServiceA Service is a stable network endpoint that load-balances traffic across a set of pods. It gets a fixed ClusterIP that never changes even as pods restart.
3metadata:
4 name: service1⚠ CRITICAL: This is the DNS name other components use. Ingress refers to this exact name. Other pods call it as "service1:5000". K8s DNS resolves "service1.default.svc.cluster.local" to its ClusterIP.
5 namespace: defaultMust match the namespace of the pods it targets AND the Ingress that references it. Resources can only reference Services in the same namespace.
6 labels:Labels on the Service object — for querying only, not for routing
7 app: service1Label on the Service itself (not the pods). Used for: kubectl get svc -l app=service1
8spec:
9 type: ClusterIPClusterIP = internal only. Gets a virtual IP accessible only within the cluster. Other types: NodePort (external via node port), LoadBalancer (cloud LB). ClusterIP + Ingress is the correct pattern for HTTP services.
10 selector:⚠ CRITICAL LINK: This is how the Service finds its pods. It looks for pods with matching labels. This is the glue between Service and Deployment.
11 app: service1Send traffic to any pod that has label "app: service1". Must match backend.yaml template.metadata.labels.app. This is the selector chain: Service → (finds pods with this label) → Pod
12 ports:Port mapping — what port the Service listens on, and what port it forwards to on the pod
13 - name: httpPort name — referenced in Ingress as the named port. Good practice for clarity.
14 protocol: TCPHTTP runs over TCP. Could be UDP for DNS or other protocols.
15 port: 5000Port the Service LISTENS on. Other components (Ingress) connect to this Service on port 5000. Must match ingress.yml backend.service.port.number
16 targetPort: 5000Port on the POD to forward traffic to. Must match containerPort in backend.yaml AND app.py port=5000. In this case port == targetPort — they could be different (e.g., Service on 80, pod on 5000).
⚠️ Why does K8s need a Service? Why not call pods directly?
Pods are ephemeral — they restart constantly and get new IP addresses every time. If Ingress pointed directly at a pod IP and that pod restarted, the IP changes and traffic breaks. A Service has a fixed ClusterIP that never changes. K8s automatically updates which pods sit behind it as pods come and go. The Service = a stable proxy in front of unstable pods.

8. ingress.yml — HTTP Router (every line)

k8s/ingress.yml
The traffic cop — looks at incoming URL paths and routes each request to the correct Service
ingress.yml
1apiVersion: networking.k8s.io/v1Networking API group — Ingress graduated to stable v1 in K8s 1.19. Use this, not the old networking.k8s.io/v1beta1.
2kind: IngressIngress = HTTP(S) routing rules. NOT a standalone component — requires an Ingress Controller (nginx-ingress) to actually process these rules.
3metadata:
4 name: app-ingressIngress object name. In Phase 3: becomes "app-ingress-dev" and "app-ingress-prod" per namespace.
5 namespace: defaultMust be in the same namespace as the Services it routes to. In Phase 3: "dev" or "prod".
6 annotations:Extra config passed to the nginx-ingress controller. Annotations are controller-specific — these are nginx-specific settings.
7 nginx.ingress.kubernetes.io/proxy-connect-timeout: "30"How long nginx waits to establish a connection to the upstream service (30 seconds). Prevents hanging requests from tying up nginx workers.
8 nginx.ingress.kubernetes.io/proxy-read-timeout: "30"How long nginx waits for the service to respond after connection is made (30 seconds). If Flask takes >30s, nginx returns 504 Gateway Timeout.
9spec:
10 ingressClassName: nginx⚠ CRITICAL: Tells K8s which Ingress Controller should handle this Ingress. "nginx" matches the IngressClass created when nginx-ingress was installed via Helm. Without this, the rules are ignored.
11 rules:The routing rules — evaluated in order from most specific to least specific
12 - http:HTTP routing block. No host specified = matches ANY hostname. In production you'd add: host: myapp.example.com
13 paths:List of path → service mappings
14 - path: /api/service1Match requests starting with /api/service1 (Prefix). e.g. /api/service1, /api/service1/orders — all go to service1
15 pathType: PrefixPrefix = match this path AND anything starting with it. "Exact" would only match /api/service1 exactly. "ImplementationSpecific" = controller decides.
16 backend:Where to forward matching requests
17 service:
18 name: service1⚠ CRITICAL LINK: Must match backend-service.yaml metadata.name exactly. This is how Ingress finds the Service.
19 port:
20 number: 5000Must match backend-service.yaml port (line 15). Ingress → Service:5000 → Pod:5000 → Flask
21 - path: /api/service2Route /api/service2/* to service2
22-26 ... (same pattern) ...service2 on port 5001, service3 on port 5002 — same structure as service1
27 - path: /⚠ Catch-all. Everything not matching /api/service* goes to frontend. This MUST be the LAST path — Ingress evaluates top to bottom; more specific paths first.
28 pathType: Prefix/ with Prefix = matches everything. Acts as the default route.
29 backend: service: name: frontend-service⚠ CRITICAL LINK: Must match service.yaml metadata.name exactly (line 4)

13. K8s Cluster Management — What Happens Internally

What happens when you run kubectl apply -f backend.yaml

StepComponentAction
1kubectlSends HTTP POST/PATCH to API Server with the YAML as JSON
2API ServerValidates the manifest, stores it in etcd (the cluster database)
3Deployment ControllerSees new Deployment in etcd, creates a ReplicaSet (the actual pod manager)
4ReplicaSet ControllerCounts existing pods vs desired (3). Creates 3 Pod objects in etcd.
5SchedulerSees 3 unscheduled pods. Evaluates nodes for CPU/RAM availability + topology spread rules. Assigns each pod to a node.
6kubelet (on each node)Sees it has a pod assigned to it. Calls Docker/containerd to pull the image and start the container.
7kubeletStarts running readinessProbe (GET /health). Reports pod status back to API Server.
8kube-proxy (on each node)Updates iptables/IPVS rules so the Service ClusterIP forwards to the new pod IPs.
9Ingress ControllerWatches for Ingress objects. Updates its nginx config to include the new Service.
10UserTraffic starts flowing to pods. Done ✅

What happens when a pod crashes

StepComponentAction
1kubeletContainer exits unexpectedly. kubelet detects exit code ≠ 0.
2kubeletReports pod status = Failed to API Server → etcd updated
3ReplicaSet ControllerSees: desired=3, actual=2. Creates a new Pod object immediately.
4SchedulerAssigns new pod to a node (respecting topology spread)
5kubeletPulls image (or uses cache if not :latest) and starts container
6kube-proxyOld pod IP removed from Service endpoints. New pod IP added after readiness passes.
7—Total recovery time: typically 5–15 seconds

What happens during a rolling update (git push → new image)

StepWhat K8s doesEffect on traffic

✅ Summary — How K8s manages the cluster in one paragraph

You declare your desired state in YAML files and apply them. Kubernetes stores this in etcd and runs continuous reconciliation loops — controllers constantly compare desired vs actual state and fix differences. The Deployment Controller ensures 3 pods always run. The ReplicaSet Controller creates/deletes pods to match. The Scheduler places pods on nodes with available resources. kubelet on each node starts/monitors containers. kube-proxy updates routing tables so Services always reach healthy pods. The Ingress Controller translates URL path rules into nginx routing config. ArgoCD adds another loop on top — ensuring the cluster always matches what's in git. If anything drifts (pod crashes, manual change, node failure), a controller notices within seconds and self-heals. You never manage individual pods — you manage desired state.
